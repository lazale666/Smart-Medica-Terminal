# Smart Medica Server 快速上手说明

## 1. 项目是什么

这是一个基于 `Python + TCP Socket + SQLite + Ollama` 的服务端程序，文件入口是 `server.py`。

它主要做三件事：

1. 提供基础的 AI 问答服务。
2. 管理医生、患者的登录与在线状态。
3. 在患者和医生之间建立会话，并转发聊天消息。

可以把它理解成一个“医疗咨询后端原型”：

- 患者可以直接问 AI。
- 患者也可以请求接入医生。
- 医生登录后会出现在在线医生列表中。
- 医患建立连接后，双方可以通过服务端转发消息。

  服务端主程序，核心逻辑都在这里。

## 4. 如何启动

### 方式一：直接双击

运行：

`启动服务器.bat`

这个脚本会做三件事：

1. 检查 Python 是否可用
2. 检查并安装 `requirements.txt` 里的依赖
3. 检查 Ollama 是否可用，然后执行 `python server.py`

```bash

```

```text

```

## 5. server.py 核心结构

`server.py` 可以拆成 6 个部分理解：

### 5.1 全局状态

包括：

- `ollm`
  Ollama 聊天模型实例
- `clients`
  当前所有 TCP 连接
- `doctors`
  当前在线医生及其会话状态
- `clients_lock`
  线程锁，避免多线程并发修改列表出问题

这里最重要的是：

- `clients` 用于统一管理连接
- `doctors` 用于医生分配、获取在线医生、消息转发

---

### 5.2 数据库初始化

函数：

- `init_database()`

启动时会创建三张表：

#### `users`

实际在使用：

- 用户注册
- 用户登录

字段：

- `id`
- `username`
- `password`
- `role`

#### `sessions`

当前仅创建表，代码里没有真正写入。

用途上看是预留给“医患会话持久化”的。

#### `messages`

当前也只是创建表，没有实际保存聊天记录。

用途上看是预留给“消息历史存储”的。

结论：

目前数据库真正启用的只有 `users` 表。

---

### 5.3 用户相关函数

#### `add_user(username, password, role='client')`

作用：

- 向 `users` 表插入一条用户记录

特点：

- 用户名唯一
- 重复插入时返回 `False`

#### `verify_user(username, password, role=None)`

作用：

- 校验用户登录信息是否正确

#### `user_exists(username, role=None)`

作用：

- 判断用户是否存在

---

### 5.4 AI 模型初始化与调用

#### `init_ollama()`

作用：

1. 检查 `http://localhost:11434` 是否可访问
2. 如果 Ollama 没启动，则尝试执行：

```bash
ollama serve
```

3. 创建：

```python
ChatOllama(model=model_name, temperature=0.7)
```

也就是说，服务启动时就会初始化 AI 模型。

#### `process_with_ollama(message)`

作用：

- 把用户消息传给本地模型
- 返回模型输出文本

调用关系：

- 当收到 `type == "message"` 的请求时调用这个函数

---

### 5.5 网络协议

这是一个自定义 TCP 协议，不是 HTTP。

每条消息格式：

1. 前 4 字节：消息体长度
2. 后面 N 字节：JSON 内容

服务端发送消息的函数：

- `send_response(client_socket, msg_dict)`

它会把 Python 字典编码为 JSON，再拼接 4 字节长度头发回客户端。

客户端如果要接入，必须遵守这个协议。

`client_test.py` 就是最小示例。

---

### 5.6 客户端处理主流程

函数：

- `handle_client(client_socket, addr)`

这是整个项目最核心的函数。

它的职责：

1. 接收 socket 数据
2. 做拆包
3. 解析 JSON
4. 根据 `type` 分发到不同逻辑
5. 连接断开时清理医生/患者关系

---

## 6. 消息类型与业务逻辑

这是你快速理解项目最关键的部分。

---

### 6.1 `login`

用途：

- 登录医生或患者

请求字段：

- `type`
- `username`
- `password`
- `role`

逻辑：

1. 调用 `verify_user()`
2. 如果校验失败，但用户不存在，则自动注册
3. 登录成功后把当前连接写入 `client_info`
4. 如果是医生，还会加入 `doctors` 列表

注意点：

- 患者角色允许空密码首次进入
- 医生登录成功后，才算“在线医生”

返回：

- `login_success`
- `login_failed`

---

### 6.2 `register`

用途：

- 显式注册账号

逻辑：

- 调用 `add_user()`

返回：

- `register_success`
- `register_failed`

---

### 6.3 `message`

用途：

- 普通 AI 问答

逻辑：

1. 提取 `data` 或 `message`
2. 调用 `process_with_ollama()`
3. 返回 AI 结果

返回：

- `ai_response`

这条路径不涉及医生。

---

### 6.4 `ping`

用途：

- 心跳检测

返回：

- `pong`

用于确认 TCP 连接仍然可用。

---

### 6.5 `get_doctors`

用途：

- 获取在线医生列表

逻辑：

- 调用 `get_online_doctors()`

返回字段包含：

- `id`
- `name`
- `online`
- `active_clients`

这里的 `id` 实际上是：

```python
id(doctor['socket'])
```

也就是 Python 运行时里 socket 对象的内存标识，不是数据库主键。

这点很重要。

---

### 6.6 `connect_doctor`

用途：

- 患者手动选择医生进行连接

请求字段重点：

- `doctor_id`
- `username`

逻辑：

1. 根据 `doctor_id` 在 `doctors` 列表里查医生
2. 如果患者已经绑定过医生，则拒绝重复连接
3. 如果找到目标医生，则建立医患关系
4. 为该关系生成 `session_id`
5. 通知患者连接成功
6. 如果是首次创建该会话，还会通知医生端来了一个新患者

返回：

- `connection_success`
- `connection_failed`

重要细节：

- 服务端会尝试复用同名患者的旧会话
- 这样患者重连时可以继续用原来的 `session_id`

---

### 6.7 `request_doctor`

用途：

- 自动分配医生

逻辑：

1. 在在线医生里选 `connected_clients` 数量最少的那个
2. 建立会话
3. 返回 `session_id`
4. 如果没有医生在线，则进入等待状态

返回：

- `connection_success`
- `waiting_for_doctor`

这就是项目里的“简单分诊逻辑”。

---

### 6.8 `doctor_message`

这是医患聊天的核心消息类型。

它分两种情况：

#### 情况 A：患者发给医生

条件：

- 当前连接角色是 `client`
- 并且已经绑定 `current_doctor`

逻辑：

- 服务端把消息转发给当前医生 socket

医生收到的消息类型是：

- `client_message`

附带：

- `sender`
- `client_name`
- `session_id`
- `message`

#### 情况 B：医生发给患者

条件：

- 当前连接角色是 `doctor`

逻辑：

1. 根据 `target_session_id` 找到目标患者
2. 把消息转发给该患者 socket

患者收到的消息类型仍然是：

- `client_message`

附带：

- `sender`
- `doctor_name`
- `session_id`
- `message`

重要点：

- 医生回消息时依赖 `target_session_id`
- 不是简单按用户名发
- 这样可以避免多个患者时发错消息

---

## 7. 连接断开时会发生什么

`handle_client()` 的 `finally` 里有清理逻辑。

### 患者断开

会做两件事：

1. 从医生的 `connected_clients` 列表里移除自己
2. 通知医生：

- `client_disconnected`

### 医生断开

会做三件事：

1. 遍历自己名下的所有患者
2. 把这些患者的 `current_doctor` 设为 `None`
3. 通知每个患者：

- `doctor_disconnected`

最后还会：

- 从 `clients` 列表移除当前连接
- 如果当前连接是医生，则从 `doctors` 列表移除

## 8. 函数调用关系梳理

你可以按下面这条主线理解调用关系：

### 启动主线

`start_server()`

调用：

1. `init_database()`
2. `init_ollama()`
3. `socket.bind()`
4. `socket.listen()`
5. 每有一个新连接，启动线程执行 `handle_client()`

### AI 问答主线

`handle_client()`
-> 收到 `type == "message"`
-> `process_with_ollama()`
-> `send_response()`

### 医生列表主线

`handle_client()`
-> 收到 `type == "get_doctors"`
-> `get_online_doctors()`
-> `send_response()`

### 手动连接医生主线

`handle_client()`
-> 收到 `type == "connect_doctor"`
-> 在 `doctors` 中查找目标
-> 建立/复用 `session_id`
-> `send_response()` 给患者
-> 必要时 `send_response()` 给医生

### 自动分配医生主线

`handle_client()`
-> 收到 `type == "request_doctor"`
-> 选择负载最小医生
-> 建立/复用 `session_id`
-> `send_response()`

### 医患消息转发主线

`handle_client()`
-> 收到 `type == "doctor_message"`
-> 判断当前连接是患者还是医生
-> 找目标 socket
-> `send_response()`

## 9. 关键运行时数据结构

### `client_info`

每个连接都会维护一个 `client_info` 字典，核心字段有：

- `socket`
- `addr`
- `name`
- `role`
- `current_doctor`
- `connected_clients`
- `doctor_session_id`

理解它很重要：

- 对患者来说，`current_doctor` 表示当前接入的医生
- 对医生来说，`connected_clients` 表示自己当前接诊的患者列表

---

### `doctors`

这是一个全局列表。

里面每个元素本质上就是某个医生连接对应的 `client_info`。

因此它不仅存在线医生，还存：

- 医生名
- socket
- 当前接诊患者列表

项目里很多核心能力都建立在这个列表上：

- 获取医生列表
- 自动分配医生
- 手动连接医生
- 医生回复患者

---

### `connected_clients`

医生对象里维护：

```python
[
    {
        "session_id": "...",
        "client": client_info
    }
]
```

它表示：

- 这个医生当前连接了哪些患者
- 每个患者对应哪个 `session_id`

---

## 10. 当前项目的优点与局限

### 优点

- 结构直观，所有主逻辑集中在 `server.py`
- AI 问答和医患聊天两条链路分得比较清楚
- 支持医生在线列表、手动连接、自动分配
- 使用 SQLite，部署简单

### 局限

- 所有业务都集中在一个文件，后续维护成本会越来越高
- `sessions` 和 `messages` 表目前没有真正使用
- 用户密码是明文存储，不适合正式环境
- `doctor_id` 使用 `id(socket)`，不适合作为长期稳定标识
- 线程 + 全局列表的方式适合原型，不适合高并发场景
- 消息协议是自定义 TCP，不如 HTTP/WebSocket 通用

---

## 11. 如果你想继续改项目，建议优先做什么

建议优先顺序：

1. 把 `server.py` 拆分成多个模块
2. 真正落库 `sessions` 和 `messages`
3. 对密码做哈希存储
4. 给医生设计稳定 ID，而不是使用 `id(socket)`
5. 补充客户端协议文档
6. 把乱码提示文案统一清理

推荐拆分方向：

- `database.py`
- `auth.py`
- `ollama_service.py`
- `protocol.py`
- `doctor_session.py`
- `server.py`

---

## 12. 最后用一句话总结

这个项目是一个“AI 问答 + 在线医生分配 + 医患消息转发”的 TCP 服务端原型，`server.py` 既是启动入口，也是全部核心业务的集中实现文件。
